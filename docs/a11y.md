# 无障碍：嵌套架构下读屏器能不能读到页面

日期：2026-10-20
问题（任务：a11y 半天验证）：嵌套合成器架构把页面放在 helper 进程的 Wayland
surface 里，读屏器（ORCA 等 AT-SPI 客户端）还能读到页面内容吗？这是与
WebKitGTK 对比时最大的功能差距假设。

## 1. 结论：能。缺口实际不存在

CEF 文档（`CefBrowserHost::SetAccessibilityState`）明文：**windowed 浏览器
在 STATE_ENABLED 下进入 Chromium 的 Complete 模式——"all platform
accessibility objects will be created and managed by Chromium's internal
implementation"**。也就是说 AT-SPI 对象（含总线注册）由 Chromium 原生创建，
客户端唯一要做的是"检测到读屏器并调用本方法"。

## 2. 实现（helper/src/main.cpp）

- `CHROMIUM_A11Y=1` 时：`OnAfterCreated` 调
  `browser->GetHost()->SetAccessibilityState(STATE_ENABLED)`（确定性启用），
  命令行追加 `--force-renderer-accessibility`（renderer 侧双保险）；
- 产品化的检测路径（监听 a11y 总线上的读屏器注册并自动调用）列为后续，
  文档原文确认客户端职责就止于此。

## 3. 实测证据（AT-SPI 总线转储）

`CHROMIUM_A11Y=1` 启动后，helper 以 `Chromium` 应用名注册到 a11y 总线
（pid 匹配 helper 进程）。Atspi 遍历其树：

```
- application: 'Chromium'
  - frame: ''
    - panel ×4
      - document web: 'A11Y Probe'
        - heading: 'CEFNest 无障碍探针'
        - paragraph: ''
        - link: '示例链接 Example link'
        - button: '测试按钮 Test button'
        - list: ''
```

中文语义、角色、名称全部正确。对照：同机 Edge（同为 Chromium 系）也在总线上。

## 4. 边界与后续

- **焦点跟随**：ORCA 默认追踪的是"聚焦窗口 → 该窗口应用的树"。宿主窗口
  （GTK 树）与 helper（Chromium 树）是总线上的两个应用，读屏器能否自动跟随
  页面内焦点需要真机人工验证（开 ORCA 实测）——这是把本项从"总线级可用"
  推进到"体验级可用"的最后一步；
- **不做**：把 Chromium 树桥接进宿主 GTK a11y 树（WebKitGTK 的模式）——
  AT-SPI 应用级分离已可用，桥接的成本数量级不同；
- 长跑与性能：Complete 模式会增加 renderer 内存与树维护开销，读屏器关闭时
  Chromium 自己会降级（STATE_DEFAULT 路径仍在）。
