# 第一部分 · 分类判据（CEF 缺口批的主结构）

每项先回答一个问题：**宿主要不要做"每次"的决定？**

- **要**（逐请求策略、落盘路径、放行与否、自绘界面）→ **接口**。组件给
  机制与安全默认，决定权全在宿主。
- **不要**（设一次值就完事）→ **组件集成**。组件把整条管道走完，宿主设
  一个属性甚至零动作。
- 中间档：有安全默认值、宿主可换自定义 UI → **接口 + 可选内置默认**，
  走本库已验证两次的惯例——`::context-menu` 返回 TRUE=宿主自绘、FALSE=
  组件弹自带 popover；`auto-source-window` 属性=内置窗口可关。

**一条铁律贯穿全批**：组件可以画"自己的"界面（popover、source window
是先例），但**凡涉及落盘路径与放行策略的界面，永远归宿主**。

### 现状锚点（已核实）

- Helper 已实现的 handler：LifeSpan、Load、Display（地址/标题）、Focus、
  Keyboard、Request（OnBeforeBrowse）、Download、Find、ContextMenu、
  Permission、RenderProcess（cefnestPostMessage 注入）。
- 控制通道命令/事件含插件批（`plugins-*`/`plugin-*`/`browsers-list` 已在
  两份 control-channel 表里）；4 MiB 行上限；页面类事件一律带 `browser`
  字段；只有 `select-browser`/`close-browser`/`load`/`js` 读取它，其余
  命令作用于活动浏览器（新命令沿用此惯例）。
- 流式先例：`view-source-begin/-chunk/-end`（64 KiB UTF-8 JSON 块、
  16 MiB 上限、第二个 begin 弃前一个）。
- parked 先例：`download-begin` 不答不写盘；`context-menu`/
  `permission-request` 不答会阻塞后续同类请求；浏览器关闭时弃单。
- Chrome 风格窗口在本进程已实测崩溃（StatusBubble 的 WaylandBubble），
  唯一例外是 ShowDevTools 的 delegate 路径——**CEF 默认 JS/文件对话框
  同属 Chrome 风格 views UI**，混合批两项需先实测现状再定内置默认的形状。

# 第二部分 · CEF 缺口

## 一、组件集成批（宿主设属性，组件全包管道）

### 1.1 代理

- **CEF 面**：Chromium `--proxy-server` / `--proxy-bypass-list` 开关（CEF
  无运行时 SetProxy，仅 context 创建时生效）。
- **形状**：session 属性 `proxy`（string，`scheme://host:port`，如
  `socks5://127.0.0.1:1080`）+ `proxy-bypass`。start() 前设置生效、start
  后设置仅下次 start（与 data-directory 同语义）；spawn 时经 env
  `CHROMIUM_HELPER_PROXY` / `CHROMIUM_HELPER_PROXY_BYPASS` 传入，helper
  在 CefInitialize 前并入 main_args；未设置必须 unsetenv（沿 DATA_DIR 的
  防污染先例）。
- **门禁**：本地起极简 HTTP 代理（python）→ 断言经代理可达/直连被断。

### 1.2 Accept-Language

- **CEF 面**：`SetAcceptLanguageList`（同样 start 前定型）。
- **形状**：与 1.1 完全同形——session 属性 → env
  `CHROMIUM_HELPER_ACCEPT_LANG` → CefInitialize 前并入。
- **门禁**：探针页读 `navigator.language` 断言。

### 1.3 Auto-Resize

- **CEF 面**：`CefBrowserHost::SetAutoResizeEnabled(enabled, min, max)`。
- **形状**：session 属性 `auto-resize`（boolean + min/max），组件内部把
  CEF 的回调接到既有 surface configure 链（这条链在组件手里：
  `nested_compositor_set_surface_size()` 已支持每 toplevel 配置尺寸）；
  `::auto-resize-updated (size)` 事件知会宿主。
- **门禁**：开属性 → 页面改 body 尺寸 → 断言 surface 尺寸跟随且 min/max
  钳住。

### 1.4 zoom-set（补全既有集成）

- **CEF 面**：`SetZoomLevel(double)`，命令族 `zoom-in/out/reset` 已存在。
- **形状**：命令 `zoom-set {level}` → 现有 `zoom` 事件回读。纯补全，无新
  管道。
- **门禁**：并入现有 zoom 断言流。

## 二、能力接口批（宿主取数据/要字节，无策略）

### 2.1 Cookies 管理

- **CEF 面**：`CefRequestContext::GetCookieManager()` 的
  `VisitUrlCookies` / `SetCookie` / `DeleteCookies`（全部异步 + 完成回调；
  cookie manager 非线程安全，一律 UI 线程 → CommandTask/EventTask 既有
  模式）。
- **命令（全部 with-receipt，宿主给 id）**：
  - `cookies-get {id, url}` → `cookies-result {id, cookies: [{name, value,
    domain, path, expires, secure, httponly}]}`；
  - `cookies-set {id, cookies: [...]}` → `cookies-result {id, ok, count}`；
  - `cookies-delete {id, url, name?}` → `cookies-result {id, deleted}`。
- **Session API**：`chromium_session_cookies_get/set/delete (self, …, id)`
  + `::cookies-result` 信号。
- **约束**：expires 为 int64 秒；与数据目录持久化天然成对——incognito
  模式下 cookies 会话内有效、退出即失，文档写明。
- **门禁**：`test/cookies-gate.sh`——探针页 `document.cookie` 写入 →
  `cookies-get` 读回比对；`cookies-set` → 页面读回。

### 2.2 打印到 PDF

- **CEF 面**：`CefBrowserHost::PrintToPDF (settings, callback)`，回调给
  整段 PDF 字节。
- **接口**：`print-pdf {id, landscape?, print_background?, page_ranges?,
  scale?}`（receipt）→ 流式三段，复刻 view-source 但 **二进制走 base64**：
  `pdf-begin {id}` / `pdf-chunk {id, data}`（base64 of 48 KiB，JSON 行不超
  64 KiB）/ `pdf-end {id, bytes}`；16 MiB 上限与截断位沿用。
- **Session API**：`chromium_session_print_pdf (self, id)` +
  `::pdf-chunk (id, GBytes)`（session 侧解 base64，宿主拿裸字节拼接）。
  写到哪个文件归宿主——与下载同一逻辑。
- **门禁**：`test/pdf-gate.sh`——校验 `%PDF-` 魔数与 `%%EOF` 尾、字节数
  >0；截断路径用人为上限触发。

### 2.3 page-text / history

- `page-text`（receipt）→ 流式 `page-text-*`（4 MiB 上限），
  `CefFrame::GetText`；
- `history`（receipt）→ `history-result {entries[]}`，`GetNavigationEntries`。

### 2.4 上报信号（fire-and-forget，自动发）

- `loading-progress {browser, progress}`（0.0–1.0，
  `OnLoadingProgressChange`）；门禁并入现有加载断言流（progress 单调）。
- `fullscreen {browser, fullscreen}`（`OnFullscreenModeChange`——helper 的
  Esc 退出与 window->SetFullscreen 已存在，只补上报）；宿主可据此镜像
  自己窗口的全屏。
- `favicon {urls[]}`（`OnFaviconURLChange`）；下载与挑选图标归宿主。

## 三、混合批（接口 + 可选内置默认）

### 3.1 JS 对话框（alert / confirm / prompt / beforeunload）

- **CEF 面**：`CefJSDialogHandler::OnJSDialog`、`OnBeforeUnloadDialog`、
  `OnResetDialogState`、`OnDialogClosed`（新增 `HelperJSDialogHandler`）。
- **分类**：唯一走 TRUE/FALSE 惯例的项。无文件系统后果，存在安全默认值
  （alert→ok；confirm→cancel；prompt→cancel+空——写进头文件注释），所以
  组件可以自带默认 UI；宿主想自绘随时接管。
- **接口**：`::js-dialog (kind, message, default_value)` 返回 gboolean——
  **TRUE=宿主自绘并应答**（`chromium_session_js_dialog_respond (self, id,
  ok, value)`，parked）；**FALSE=组件弹自己的 GTK 对话框**（非 Chrome
  风格 views，无 StatusBubble 崩溃面；先实测）。**无人连接=安全默认应答**，
  与"不接即拒"的页面权限先例一致。
- **形状**：`js-dialog {browser, id, kind: alert|confirm|prompt|
  beforeunload, origin, message, default_value}`；`js-dialog-respond {id,
  ok, value}`；`js-dialog-closed {id}`（宿主自绘 UI 的收尾）；beforeunload
  复用同一事件流（kind 区分）。
- **阻塞语义**：JS 对话框悬着时页面 JS 全部挂起——与 context-menu 的
  "不答阻塞后续右键"同类，文档写明；浏览器关闭时 OnBeforeClose 弃单。
- **前置实测**：CEF 默认对话框在本进程的现状（只说"大概率异常"）——探针
  页触发 alert 看行为，再定内置默认用 GTK 对话框还是纯默认应答。
- **门禁**：`test/js-dialog-gate.sh`——三种对话框触发、应答、页面状态
  回写（prompt 的 value 回填页面 div）；自绘路径（TRUE）与默认路径
  （FALSE/未连接）各一轮。

### 3.2 文件对话框（上传/另存）

- **CEF 面**：`CefDialogHandler::OnFileDialog`（mode: OPEN/MULTIPLE/
  OPEN_FOLDER/SAVE；accept_filters）。
- **接口**：`file-dialog {browser, id, mode, title, default_path,
  accept[]}` parked；`file-dialog-respond {id, paths[]}`（**空数组=取消**）
  → `callback->Continue(paths)`。
- **默认拒绝的理由**：与下载同一铁律——文件从哪来、到哪去是宿主的安全
  决定，组件不代选。GTK 文件选择器是宿主强项（`examples/` 出用例）。
- **Session API**：`::file-dialog (mode, title, accept)` +
  `chromium_session_file_dialog_respond (self, id, paths)`。
- **门禁**：`test/file-dialog-gate.sh`——`<input type=file>` 页 + 脚本
  应答路径，断言 upload 控件拿到文件名；不答=取消路径也断言。

## 四、策略接口批（宿主每次决定；默认值全部是"不"）

### 4.1 证书错误豁免

- **CEF 面**：`OnCertificateError`（RequestHandler 已挂，补实现）；
  `OnSelectClientCertificate` 可选同批。
- **接口**：默认 deny（Chrome 语义）。`certificate-error {browser, error,
  url, subject, issuer, fingerprint}` parked；`certificate-respond {allow}`
  → `callback->Continue`。**策略豁免机制**：`certificate-authorize
  {fingerprint}`——helper 内存指纹表，命中自动放行不再询问；helper 生命周期
  内有效（跨重启由宿主自己的策略存储负责，helper 不持久化）。
- **门禁**：单元级（门禁里起不了真实 TLS）——注入式断言或手动验收，实施
  时定。

### 4.2 资源拦截一期（咨询式）

- **CEF 面**：`GetResourceRequestHandler` + `OnBeforeResourceLoad`
  （RequestHandler 已挂，补工厂与匹配）。
- **过滤注册**：`intercept-add {id, patterns: ["*://ads.example/*", …],
  resource_types?: [...]}` / `intercept-remove {id}`——通配 `*`/`?`，helper
  内存表；**无注册=零开销直通**（默认关）。
- **咨询流**：命中 → `request-intercept {request_id, url, method,
  resource_type, is_main_frame, headers{}}` parked → 宿主
  `request-respond {request_id, action: allow|cancel|redirect, url?}` →
  `Continue/Cancel`（redirect 先 `SetURL`）。
- **观测模式**：`intercept-mode {passive}`——事件照发但不阻塞，供统计。
- **语义约束**：每次命中引入宿主往返延迟，文档写明宿主必须快答；无超时
  （与 context-menu 一致），浏览器关闭弃单。
- **层界**：请求级拦截是组件层 API——Web 插件不做请求级干预（插件非目标
  不变）；原生前端经宿主进程天然可用。
- **门禁**：`test/intercept-gate.sh`——cancel 断言 img 失败；redirect
  断言换源加载；passive 断言照常加载且事件到达。

### 4.3 DevTools 协议管道

- **CEF 面**：`SendDevToolsMessage` +
  `CefDevToolsMessageObserver::OnDevToolsMessage/OnDevToolsAgentAttached`。
- **接口**：`cdp-execute {id, method, params}`（id 宿主管，透传）→
  `cdp-result {id, json}`；`cdp-event {json}` 直通。
- **约束**：4 MiB 单行上限（超限回 `status: cdp-too-large`）；**需显式命令
  启用观察者**（等于把页面全权交出，开关默认关）；`GetDevToolsUrl` 不在
  CEF 156 公开 API，外部 chrome://inspect 接入不做。
- **层界**：CDP 同为组件层 API，Web 插件不获得。
- **门禁**：`test/cdp-gate.sh`——`Runtime.evaluate` 与现有 `js` 命令对比
  同值；`Page.captureScreenshot` 截断路径。

### 4.4 资源拦截二期（响应过滤）——接口壳 + 集成芯，单独成文

- **CEF 面**：`GetResourceResponseFilter` + `CefResponseFilter`。
- **形状**：`filter-add {id, patterns, ops: [{type: replace|inject-css|
  drop-header, …}]}`——**声明式集成**：规则引擎长在组件/-helper 里，宿主
  只声明规则不写回调；通用脚本过滤不做（流式跨 chunk 正则边界复杂）。
  本批只留接口位，立项另写文档。

## 五、6.1 搭法二配对（其余项的样板，先做）

### 5.1 接口草案（实测通过才落）

```c
/* ChromiumSession 新增：browser id → 它自己的 NestedSurface。 */
NestedSurface *chromium_session_get_browser_surface (ChromiumSession *self,
                                                     int id);
/* ::browser-surface (id, surface)：surface 可能早于或晚于
 * ::browser-created 到，两个方向都要能应答；surface 消失时同 id 再发
 * 一次 NULL。 */
```

### 5.2 实测方案（门槛，先于一切实现）

配对依据是"helper 的 CefWindow 创建与控制通道事件跑在同一个 CEF UI 线程，
所以第 N 个 windowed browser 与第 N 个新 toplevel 同序"——这目前是**论证**，
不是实测。按原插件计划 §六.8 定下的清单测，一项不多一项不少：

1. popup 与 options **同开**；
2. 关掉一个**再开另一个**（地址复用的坑就在这）；
3. **devtools 也开着**（多一路 toplevel 干扰）；
4. `--plugin-dir` 下**四个插件同时开弹出页**。

每种情形断言"这块 surface 上的画面属于这个 id"——用 pixel gate 的取帧
办法对画面做内容断言（每插件一个独特纯色页）。驱动脚本
`test/surface-pair-gate.sh`（真桌面跑，无头 mutter 的时钟节奏会让内容
断言失真——frame-stop 的教训）。

**判定**：四场景全过 → 落 5.1 的接口，配对依据写成实测事实；任何一场景
不过 → **不加接口**，搭法二在本组件层就是"宿主自担风险的写法"，记下实测
数据后本项终止，其余项不受影响。

### 5.3 配对成立后：搭法二的宿主形态（demo 升级，非库功能）

- 弹出页：`GtkPopover` 挂在 action 按钮下，`set_surface_size()` 喂
  `cefnest.popup` 的钳位尺寸，收起时 `set_frames_suspended(TRUE)`，
  Tab 用 `advance_page_focus()/release_chain_focus()` 走链；
- 设置页：`options-open-in-tab` 假 → 宿主窗口的 `GtkNotebook` 页，
  真 → 沿搭法一开窗；
- demo 两形态各做一份，作为机制的验收，不作为库的承诺。

## 六、6.2 后台页

**前置（硬的）**：任何新 CefBrowser 都会在嵌套合成器上映出一个 toplevel，
FIFO 认领会把它当成下一个窗口的画面对。所以：

1. `browser-created` 事件加 `background` 布尔（helper 在 `new-browser`
   命令加 `mode: "background"`；CEF 侧隐藏窗口的形状用现有
   `frames_suspended` 机制，不新建机制）；
2. demo 的 `assign_browser_surfaces()` 跳过带标志的 browser；gate 断言
   "背景 browser 不占 FIFO 位、后续窗口认领不错位"；
3. 然后才谈语义：manifest 的 `background.service_worker` 从
   `unsupported-field` 警告转正——形状是"常驻隐藏 browser 跑清单指定页"，
   **不承诺** Chrome 的完整 service worker 语义（事件生命周期、
   wake/suspend），做到哪一步写进 docs/plugins.md。

风险：隐藏 browser 的帧停摆与 `::closed`/`stop()` 的清理路径都要过
`G_DEBUG=fatal-criticals` 的两轮装卸（沿用 plugin gate 第 7 条的模式）。

## 七、6.3 tabs 扩面

数据源就是 `g_browser_slots` 与 host 的现取接口，按"拿得到就给"扩：

- 计划纳入：`audible`/`muted`（`IsAudioMuted()`）、`zoom`（`GetZoomLevel()`）、
  `windowed`；`pinned` 与 `discarded` **不做**（CEF 槽位表里没有，造数即
  谎报）；
- `tabs.update` 补 `muted`；
- 文档同步 `docs/plugins.md` 的 API 子集表与 `docs/control-channel.md` 的
  `browsers` 事件行；
- 门禁：plugin gate 加断言（两浏览器一静音一有声，query 的字段各自正确）。

## 八、6.4 权限接口化（用户 2026-10-26 裁定）

**裁定**：权限提示做成组件接口，画法留给开发者自定义。组件持有"挂起的
enable"这个机制，对话框/浮层/行内开关全是宿主的事——组件一行 UI 都不画。

### 8.1 现状与缺口

`::grant-request (id, permissions)` 是**同步**形态：答案就是权限表，宿主在
发射返回前调 `grant()` 则本次 enable 完成，否则
`G_IO_ERROR_PERMISSION_DENIED`、宿主稍后重新 enable。这验证了"同步宿主"
（P2），但一个真对话框跑在主循环上，发射早已返回——它只能拿到 FALSE 再
重新调一次。缺的是 **parked 形态**：请求作为对象挂起，宿主（或没人）应答
之前，enable 不落定。

### 8.2 接口草案

```c
/* ::grant-request 签名升级（0.0.1 无 ABI 负担）：
 *   ::grant-request (id, permissions, request)
 * request 是组件持有的 parked 对象；不连接信号 = 立即按表裁决
 * （今天的行为，默认拒绝不变）。 */
typedef struct _ChromiumPluginPermissionRequest
    ChromiumPluginPermissionRequest;

/* 三支笔，全部以权限表为唯一事实来源（插件计划规则 3 不破）：
 *   accept()  = 把 pending 集合全部 grant()，然后落定本次 enable；
 *   deny()    = 表不动，落定为拒绝；
 *   settle()  = 不动表，按当前表落定——per-permission 的路径：
 *               宿主对单个权限调 grant()，再 settle() 收口。 */
void chromium_plugin_permission_request_accept (ChromiumPluginPermissionRequest *self);
void chromium_plugin_permission_request_deny   (ChromiumPluginPermissionRequest *self);
void chromium_plugin_permission_request_settle (ChromiumPluginPermissionRequest *self);
/* 只读：id 与 pending 集合，宿主画行用。 */
const char       *chromium_plugin_permission_request_get_id         (ChromiumPluginPermissionRequest *self);
const char *const *chromium_plugin_permission_request_get_permissions (ChromiumPluginPermissionRequest *self);
```

### 8.3 语义

| 情形 | 行为 |
| --- | --- |
| 无人连接信号 | 同今天：按表立即裁决，默认拒绝——无对话框的宿主零开销 |
| 连接了、在发射返回前应答 | 与今天等价（同步宿主继续工作） |
| 连接了、稍后应答 | enable 挂起；accept/deny/settle 落定后 manager 发 `::changed` |
| 请求悬着时插件被 disable / 模型重扫丢行 / manager dispose | 请求作废，再调三支笔是安全的 no-op；不补发事件（行都没了，无处显示） |
| 同一插件并发的第二次 enable | 第二次直接按表裁决（挂起的是第一次的 enable；表只增不减，二次结果一致） |

### 8.4 实现落点

- `src/chromium-plugin.{c,h}`：请求对象（final type，refcounted）、信号
  签名加参、enable 的挂起/落定路径；
- `examples/plugins.c`：`GtkMessageDialog` 形态的使用示例（per-permission
  行 + 允许/拒绝）——这是接口的**用法示例**，不是库功能；
- demo 同步换用新形态；`test/plugin-model.c` 加 parked 用例（应答前状态、
  三支笔、作废 no-op、二次 enable）。

# 第四部分 · 通用工程约束（全批适用）

1. 新命令默认作用于活动浏览器；带 `browser` 字段的可指定（沿用惯例，
   helper 端 `FindSlotForBrowser` + 活动回退）。
2. 单行 4 MiB 通道上限；二进制一律 base64 分块（48 KiB 明文 → 64 KiB
   行），16 MiB 流式上限与截断位沿用 view-source。
3. parked 单据在浏览器关闭（OnBeforeClose）时弃单并回 `*-dismissed` 类
   事件（新增的每种 parked 都带），宿主 UI 不留死等待。
4. 新 handler 一律 UI 线程收发（CommandTask/EventTask 既有模式）；cookie/
   PDF/CDP 的异步完成回调同样回 UI 线程后再上通道。
5. 每个特性一个 `test/<name>-gate.sh`，注册进 `test/ci-all.sh`；接口文档
   同步 `docs/control-channel.md`/`.zh-CN.md` 双语表（插件行的先例已在，
   本计划各行一次合并提交）。
6. 安全边界：拦截与 CDP 等于把页面全权交给宿主——开关默认关（无注册=
   直通；CDP 需显式启用）；文件/证书的默认答案是"不"。
7. 组件层不画授权/策略 UI：权限**接口**、文件对话框、证书提示都在组件是
   机制，对话框永远在宿主与 examples。
